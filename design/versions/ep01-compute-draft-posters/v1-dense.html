Databricks at Scale · Episode 01

What you're actually
running on

Most people learn Databricks as “the place my notebooks run.” That’s enough to be productive — not enough to be accountable for the bill.
It runs across two accounts

Control plane Databricks’ account

The UI, notebook source, the job scheduler, table metadata.

Data plane your cloud account

Cluster VMs launch here. Your storage — data never leaves.

Which is why you’re billed twice: DBUs to Databricks, VMs to your cloud provider.
Four kinds of compute — pick by workload, not habit
1
All-purpose
Interactive development, shared exploration
Runs untilsomeone stops it
2
Job cluster
Anything scheduled — train, score, monitor
Runs untilthe job ends
3
Serverless
Short, bursty, unpredictable work
Runs untilthe request ends
4
SQL warehouse
SQL, dashboards, BI tools
Runs untilauto-stop kicks in
The most common wasted spend in any workspace is #1, left running. It never raises an incident. It just bills.
The two knobs that move the bill

Spot vs on-demand

Spot is discounted capacity that can be reclaimed.
On-demand
Driver
Lose it → the whole run dies
Spot
Workers
Lose one → the task just retries
Take the discount where interruption is survivable. Pay full price where it isn’t.

Photon

A vectorised engine — it accelerates only some work.
✓
SQL & DataFrame steps. Feature builds, aggregations, joins.
✕
Python on the driver. An XGBoost fit in pandas has nothing vectorised to accelerate.
Enabling it everywhere isn’t diligence. It’s a premium paid for no gain.
Every compute setting is buying something at a price. If you can’t say what it bought you, you didn’t choose it — you inherited it.
